# PerPress 表单编排（并行/串行）+ 任务级接口流量占比 实施计划

## Context

当前表单脚本的接口只能线性串行执行（单 ThreadGroup 内顺序 Sampler），且三种压测模式的压力参数（threads/TPS）只有总量维度，无法表达"接口 A 占 70% 流量、接口 B 占 30%"这类核心压测场景。本次增强两个能力：

1. **表单脚本支持接口编排**：接口之间可标记并行或串行
2. **任务创建支持每接口流量占比**：CONCURRENT/FIXED_TPS/STEPPED 三种模式下，压力总量按占比拆分到各接口，含整数余数拆分与最小压力校验

技术基础：平台走 JMeter **零插件**路线，原生能力下：
- **接口串行** = 同一 ThreadGroup 内顺序执行（现状）
- **接口并行 + 精确流量占比** = 每接口独立 ThreadGroup，threads/TPS 按占比拆分（TG 间天然并行，PTT/TG 属性可独立控制）
- 串行链内的单个接口**无法**用原生能力精确控制占比（需插件），V1 不支持——占比单元为"执行单元"（并行接口各自一个单元、串行组整体一个单元）

## 一、数据模型（DB 无变更，均为 JSON 字段）

### FormDef 增加 groups（script.form_def）

```
FormDef{ threadGroupName, thinkTimeMs, samplers?(旧字段保留), groups?: [Group] }
Group{ name, execution: 'SERIAL'|'PARALLEL', samplers: [Sampler] }
```

- 归一化：formDef 无 groups → 视为单个 SERIAL 组（**完全向后兼容**，旧脚本零迁移）
- **SERIAL 组** → 渲染 1 个 TG，组内采样器顺序执行，共享该组压力
- **PARALLEL 组** → 组内每接口各渲染 1 个 TG（彼此并行）
- 占比"执行单元"：每个 SERIAL 组 1 个单元；PARALLEL 组内每接口 1 个单元
- 组间天然并行（多 TG 并行）；组间串行（TestPlan.serialize_threadgroups）V1 不做
- 组数上限 10，每组 samplers 非空

### TaskCreateRequest.Config 增加 weights

```
weights: List<Integer>  // 按执行单元展开顺序的整数百分比（1-100，Σ=100）
```

- 仅 FORM 脚本可用（IMPORTED 传 weights 报错）
- 多单元任务 weights 必填（前端默认均分自动填好）；单单元不传或 [100]

## 二、JMX 生成（FormScriptJmxBuilder.java）

### 新增 normalizeGroups(def) → List<Group>

无 groups 时包成单 SERIAL 组（samplers 原样）。后续渲染全部基于归一化结果。

### 渲染规则

| 模式 | 单 SERIAL 组（兼容分支） | 多单元 |
|---|---|---|
| CONCURRENT | 现状：单 TG `threads/rampup/duration` | 每单元 1 个 TG，prefix=`tg{unitIdx}`，`tg{i}.threads` |
| FIXED_TPS | 现状：tg0 + PTT | 每单元 1 个 TG + 各挂 PTT，`tg{i}.tpsPerMin` |
| STEPPED | 现状：tg{seg} 堆叠 | 每段×每单元：prefix=`tg{seg}x{unitIdx}`，每 TG 挂该单元采样器副本（TPS 单位再挂 PTT） |

- **JMX 内嵌默认值 = 服务端按占比算好的绝对值**（不引入 weight 属性让 JMeter 端计算）；`-J` 下发同名 key 覆盖（Agent 现有 buildCommand 全量透传 props，无需改动）
- **兼容性硬要求**：单 SERIAL 组路径的输出与改造前**逐字节一致**（用旧 formDef 回归 diff 验证）
- STEPPED×多单元 TG 总数 = 段数×单元数（如 5 段×3 单元=15 个 TG），JMX 百 KB 级可接受；前端在段数×单元数 > 20 时黄色提示

## 三、任务侧拆分与校验（TaskService.java）

### 拆分算法（新增 splitByWeights）

```
splitByWeights(total, weights) -> long[]   // Σ=total
  base[u] = total * w[u] / 100（整数）
  remainder = total - Σbase，按占比降序逐个 +1（占比相同按单元序）
之后每单元复用现有 share()/shareLong() 拆到节点（余数补前几节点，每节点最小 1）
```

- CONCURRENT：`tg{u}.threads = share(split(threads)[u], nodeCount, i)`
- FIXED_TPS：`tg{u}.threads = share(min(tps*2,2000)*w[u]/100 分配后)`、`tg{u}.tpsPerMin = shareLong(splitLong(tps*60)[u], nodeCount, i)`
- STEPPED：每段 value 先按占比拆，再按节点拆，写 `tg{seg}x{u}.*`

### 校验清单（validateConfig / validateRequest，中文报错）

1. weights 仅 FORM 脚本可用；每项整数 1–100；Σ=100（报错显示当前总和）；长度=单元数
2. 最小拆分校验：`单元量 < nodeCount × 最小需求` 时报错并提示所需总量，如「组A 按 5% 仅分得 4 并发，低于节点数 5，总并发需 ≥100」：
   - CONCURRENT：每单元每节点 threads ≥ 1 → `floor(threads×pct/100) ≥ nodeCount`
   - FIXED_TPS：每单元每节点 tpsPerMin ≥ 1 → `floor(tps×pct/100) ≥ nodeCount`（同时 threads 拆分结果 ≥1）
   - STEPPED：每段逐单元同上（THREADS 单位查 threads，TPS 单位查 tpsPerMin）
3. 单元数由 formDef 归一化得出，服务端不信任前端传的单元数

## 七、导入 JMX 转表单——分析结论（按用户要求仅分析不实现）

**开源界无现成能力**：
- MeterSphere：JMX 导入后仅只读展示场景树 + 辅助编辑（变量/断言），**不支持反向解析为可视化表单再回写**
- Apache JMeter 官方：无此能力
- OctoPerf / BlazeMeter：商业闭源 SaaS，实现不可借鉴
- 结论：无开源实现可直接引用

**技术可行性**：可行但成本高。JMX 元素空间巨大（控制器/定时器/前置后置处理器/JSR223/变量/函数），完整反向工程等于半个 JMeter 解析器。若未来做，建议**白名单解析**：仅接受「TestPlan→ThreadGroup→HTTPSamplerProxy/HeaderManager/ResponseAssertion/CSVDataSet/ConstantTimer」扁平结构（与本系统 builder 输出对称），遇不支持元素明确报"该 JMX 含表单不支持的元素 X，无法转表单编辑"。本平台 ScriptService 已有 CSV_FILENAME_PATTERN 解析先例，正则/逐节点解析基础已具备。
